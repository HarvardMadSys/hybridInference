# 配置归属与发行版扩展的最终边界

本记录取代同日 `2026-10-19-distribution-delivery-boundary.zh.md` 中的两项过渡安排：核心维护发行版历史键名清单，以及发行版兼容旧核心。发送接口、数据库优先级、秘密遮蔽和运行时刷新要求不变。

## 目标

核心只认识通用配置归属，不知道任何发行版的历史配置名称。发行版负责注册自己的配置、迁移自己的历史数据，并选择配套的核心版本。没有加载对应扩展时，该扩展的数据不能出现在配置列表、导出、解析结果或普通写入入口中。

## 存储与迁移

`app_config` 增加可空 `owner`：`core`、`custom` 或 `extension:<稳定标识>`。旧行的空值表示尚未归属，不能被自动当作自定义配置。核心可以认领精确匹配当前核心注册项的历史行；发行版通过通用迁移接口认领自己声明的历史键。

迁移只更新归属并单向提升秘密标记，保留配置值、来源、reset 标记、原更新时间和操作者。迁移 ID、所有者与声明摘要持久化；重复执行同一声明是幂等操作，同 ID 不同声明或跨所有者冲突使整个事务失败。schema、认领、环境导入和秘密升级使用现有配置 advisory transaction lock；提交成功后才更新进程缓存。

未归属的未知旧行保持原样并隔离。数据库本身没有足够信息区分旧发行版字段与真正的自定义变量；`source=admin`、变量名称或模型 YAML 引用都不能替代所有权。运维人员确认后，通过显式 CLI 操作认领为 custom；一般配置 PATCH 不能隐式接管。新建自定义变量必须明确写入 custom 归属。

归属检查覆盖配置列举、解析、环境回退、导出，以及写入、重置、删除、仅提升秘密标记和生成默认秘密的路径。没有加载的扩展或归属不匹配的行不可因为同名环境变量、reset 或 YAML 引用重新生效。SQL 冲突写入也检查预期所有者，不能只依赖进程缓存。

## 配套发布

扩展直接依赖正式配置归属与发送接口，缺失时启动失败。删除旧核心探测、静默 no-op、缺失接口后继续运行的分支，以及只用于旧宿主的 UI 文案补丁。

staging 从发行版提交读取完整核心 commit pin，并将这一组合写入构建证据。核心分支推进不自动改变 pin；扩展变更和核心 pin 在同一发行版提交中切换。先发布固定现有组合的构建机制，再提交核心新接口，最后提交扩展清理和新的 pin。

旧二进制不理解 owner，不能和新版本混跑。迁移发布必须停止旧 worker 后再启动新组合；当前 staging 的单实例 OnDelete 发布需要在执行前重新核实。保留旧数据不表示允许随意回滚旧程序：回滚需要同时恢复匹配的核心、发行版和数据归属契约。

生产仍沿用已验收镜像、发布证据和正式锁文件流程。本次变更不解除生产脚本的核心版本升级限制，也不把 staging 数据库迁移成功当作生产迁移或恢复证明。

## 验证

测试仅在腾讯 DevCloud 的隔离环境执行。除通用配置和发送回归外，真实 PostgreSQL 必须覆盖旧表迁移、reset/secret/元数据保留、幂等与摘要冲突、跨 owner 拒绝、确定性的并发锁等待，以及卸载扩展后的解析隔离。发行版测试覆盖完整历史键名单和原有 SES/SMS 行为。构建测试验证固定组合、过期候选拒绝及来源证据；staging 验收验证实际迁移结果和页面/API 行为。
