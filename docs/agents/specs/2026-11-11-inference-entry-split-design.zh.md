## 1. 问题

```text
客户端 / SDK ─▶ 入口（CDN、隧道或负载均衡，由发行版提供）
                  │  所有路径
                  ▼
            Next.js 控制台 ─┬─▶ 网关（/v1、/anthropic、/auth、/user、/admin …）
                            └─▶ 自己的页面
```

控制台既提供网页，也转发推理 API。一次长流式请求要经过两个都会被发布的进程（控制台、网关），任何一个重启都会打断它。

背景事实：

- 控制台的转发是自己写的反向代理（`apps/frontend/src/lib/server/gatewayProxy.ts`）：逐字节转发、不缓冲，调用方挂断就取消网关请求，不设总时长，只在连接双向静默 1 小时后关闭，失败不重试，网关连不上时回 JSON 502、静默超时回 JSON 504。API key 在网关校验，控制台不鉴权。
- 网关收到停止信号后，进行中的请求只有 5 秒，之后被取消。否则流会拖到被强杀，请求日志和费用来不及落盘。所以每次后端发布都会打断超过 5 秒的流。
- 前端的新旧 Pod 交接由发行版实现，原则可以借用（先确认、后删除；“入口停止分配”和“已有请求完成”分别确认），但实现和时限要对后端重新验证。
- 前端发布和后端发布各自造成多少中断，没有测量过。一次发布可能同时重启两个服务，一次重启打断多少请求取决于当时的在途流，所以不能用提交占比推断。

目标：

1. 网页发布期间，已开始的推理请求完整结束，新的推理请求正常成功。
2. 用对照实验回答“绕过 Next.js 是否改善端到端 latency”，结论可以是“没有明显差别”。
3. 给出后端并存发布的设计，并列出进入实现之前必须通过的门槛。

非目标：改变对外地址；移动 `/v1`、`/anthropic` 以外的接口（浏览器里的 playground 长流 `/internal/playground` 仍经控制台，这是接受的遗留）；删除内置转发（它是默认拓扑，也是回滚目标）；增加独立代理服务或把 nginx 加回来；为分流放宽网关的全局信任；自带 Compose 部署的新旧后端并存；跨服务器切换。

## 2. 目标路径与职责

```text
客户端 / SDK ─▶ 入口（同一个域名）
                  ├─ /v1、/anthropic ───────────────▶ 网关 ─▶ 模型服务
                  └─ 其余路径 ─▶ Next.js 控制台 ─┬─▶ 网关（浏览器接口，保持现状）
                                                 └─▶ 自己的页面
```

核心同时支持两种拓扑，对外行为一致：

| 拓扑 | 谁把 `/v1`、`/anthropic` 交给网关 | 用在哪里 |
|---|---|---|
| 内置转发（默认） | 控制台的 route handler | example、本地、单端口部署、入口不能按路径分流的部署 |
| 入口分流（发行版选择） | 发行版的入口 | 入口能按路径分流的部署 |

启用分流的部署里，控制台镜像不变，它的转发仍在。撤掉入口的两条规则，流量自动回到它，不需要回退镜像。

核心负责：公开路径清单和比对测试；内置转发；网关在两种拓扑下行为一致（第 5 节）；入口约定的文档；外部探针；网关的交接接口。

发行版负责：决定是否启用并配置入口规则（核心不提供入口配置）；提供入口能力和信任配置的实测证据；在自己的 staging 跑验收和实验并保留结果；发布编排。

入口约定 E1 到 E9（只把两个前缀交给网关且在解析 `.`、`..` 和百分号编码之后匹配；不缓冲；空闲超时大于 `REQUEST_TIMEOUT_SECONDS`；请求体上限不低于网关；客户端断开时关闭到网关的请求；覆盖客户端送来的来源头；网关端口只有入口和控制台能连；已发给网关的 `POST` 不自动重发；摘除实例时不关闭已建立的连接）写在[部署指南](../../developer/deployment.md#splitting-inference-traffic-at-the-entry)。

### 公开路径清单

清单原本分散写在四处（route 文件、`rewrites()`、`middleware.ts` 的 matcher、`redirects()` 的正则），靠四个测试和一份文档对齐。入口规则会是第五处，所以 `deploy/public-paths.json` 成为唯一来源：

- 每项有 `path`、`match`（`exact` 或 `prefix`，prefix 与 `isUnder` 相同：等于该前缀，或以前缀加 `/` 开头，在解析点号段之后判断）、`owner` 和 `entry_split`。只有 `/v1` 和 `/anthropic` 标为 `true`。以后多分一个前缀，改这个字段并重走验收。
- 清单里没有的网关路径不得从公网到达，清单里没有的其他路径归控制台。
- 前端测试把手写的路由列表、matcher、`redirects()` 和 `rewrites()` 与清单比对。matcher 仍是字面量（Next 构建时读取），由测试保证一致。探针也读清单。
- 核心不生成入口配置，规则由发行版手写，探针负责发现写错。

example 和本地开发继续用内置转发，一个端口、同源，不需要入口。

## 3. 必须保留的行为

分流后下列行为必须不变，由入口约定或网关保证，探针从外部检查：

| 行为 | 保证 |
|---|---|
| 鉴权 | 网关校验 API key，无 key、错 key、被停用的 key 返回与原路径相同的状态码和错误体 |
| 公开路径边界 | 入口 E1、E7。`/docs`、`/redoc`、`/openapi.json`、`/health/deep`、未公开的 `/internal/*`、`/v1/%2e%2e/openapi.json`、`//v1` 等都拿不到网关的未公开内容。这些网关路径今天只是因为控制台没有对应转发才被挡在外面 |
| 流式输出 | 入口不缓冲（E2）。合成上游按固定间隔发带序号的帧，客户端收到的间隔和序号与发出的一致 |
| 客户端取消 | 入口 E5。客户端中途断开后，网关记录该请求被取消，上游连接关闭 |
| 超时、请求体大小 | 入口 E3、E4。超过时拿到的是网关的 504 / 413，不是入口的 |
| 尾斜杠 | 在两个分流前缀上，网关返回 308，`Location` 只含路径、保留查询串、每次去掉一个斜杠，与控制台一致。网关原来按 `Host` 拼绝对地址且协议固定为 `http`，在终止 TLS 的入口后面是错的 |
| 安全响应头 | 网关给每个响应加 `X-Content-Type-Options: nosniff`。控制台另加的 `X-Frame-Options`、`Referrer-Policy` 只对网页有意义，分流路径上不再出现 |
| 同源、cookie、CORS | 域名和路径不变，不受影响 |

已知变化，写进发布说明：网关连不上时由入口返回 502 / 503 / 504，响应体是入口自己的，不保证是 JSON（发行版可以在入口配置 JSON 错误体）；少两个安全响应头。

判断请求走了哪条路径，依据网关请求日志的 `peer_ip` 和入口的访问日志，两者对得上才算证明。`Via` 头可选，不能单独作为证明。

### 3.1 入口直连时的身份与就绪

目标是推理不依赖前端，所以在前端全部停止时必须仍然成立：经入口直连的请求客户端身份照常解析；网关的 `/health/ready` 保持通过，入口不会因此摘掉网关。

约束：不为分流放宽全局信任。不关闭 `TRUST_PROXY_HEADERS`，不把包含其他工作负载的网段加进信任列表，不在代理发现模式下恢复静态列表作为回退，不把 `unknown` 身份当作正常结果放行。

客户端 IP 只在 `apps/backend/serving/utils/request_ip.py` 判定，用于请求日志、按 IP 限流、鉴权失败封禁、粘性路由和 `api_logs`。控制台只转发来源头，不为它作证。

**静态信任。** 就绪不依赖代理，前端停止不影响它。把入口在网关眼中的精确对端地址加入对应信任项（写 `X-Forwarded-For` 的入口加入 `TRUSTED_PROXIES`，Cloudflare 加入 `TRUSTED_CLOUDFLARE_NETWORKS`），保留控制台的地址。范围只能是入口自己；如果入口的对端地址与其他进程无法区分（例如同机回环端口映射后所有本机进程是同一个地址），要先解决这一点，不能用“信任这个共用地址”代替。

**Kubernetes 代理发现。** 它的配置只有一组命名空间、Service、Service UID 和直接控制器 UID，不在这组 Pod 里的对端一律是 `unknown`。在这种部署上，按今天的实现分流达不到目标：

1. 入口不在被发现的 Service 里，经入口的请求身份全部是 `unknown`。
2. 该模式开启且 `TRUST_PROXY_HEADERS` 为真时，`/health/ready` 要求代理成员非空且未过期，否则返回 503 `proxy_discovery_unavailable`。前端全部停止时成员为空，入口随即摘掉网关，前端停止直接造成推理中断。
3. 被固定的是 Pod 的直接控制器 UID。前端用 Deployment 时，每次前端发布换 ReplicaSet，新 Pod 不被承认，需要改 UID 并重启网关，而阶段二完成之前重启网关就是打断推理。

要启用分流，核心需要先满足下面的要求（尚未实现，只在第一个发行版确实使用该模式时才做）：

| # | 要求 |
|---|---|
| T1 | 入口是独立命名的信任来源，与前端来源分开配置，校验强度不低于现有来源：精确地址、固定的身份标识、快照有时效、读取失败时不给信任 |
| T2 | 每个请求的身份只由它的实际对端所属的来源决定。一个来源为空或失效，不影响另一个来源的请求。不属于任何来源的对端仍是 `unknown` |
| T3 | 就绪由“能把流量直接送到网关的来源”决定：入口来源非空且未过期即通过，不要求前端来源非空。前端来源为空或失效在 `/health/ready` 响应体和告警里报告，但不改变就绪结果 |
| T4 | 来源的身份标识在该来源正常发布后保持有效，不需要重启网关，前端来源也一样 |
| T5 | 入口不是 Pod（例如云负载均衡直连）时需要同样精确、同样会失效的来源形式，方案等部署侧证据 |

T3 改变了失效时的表现：前端来源失效时网关不再整体退出服务，只让来自前端的请求身份变成 `unknown`。没有任何新的对端被信任，但需要评审确认。

## 4. 后端并存发布（阶段二）

放在分流之后，是因为分流之后推理请求在网关前只有入口，不必再处理控制台转发在后端换实例时的连接复用（控制台转发失败不重试）。

### 4.1 单实例与并存

单实例部署保持现状：收到停止信号后 5 秒取消、落盘、退出。这是有损重启。把 5 秒直接调大没有用，因为单个实例停止接受连接之后，新请求在整个等待期间都失败。下面的排空策略只用于新旧实例并存的部署，是独立的一条路径。

### 4.2 退出条件

旧实例只有在三个条件全部确认之后才被停止。条件是状态，不是时间，也不按历史分位数截断长流：

| # | 条件 | 怎么确认 |
|---|---|---|
| X1 | 入口已停止向旧实例分配新请求 | 入口侧显示已摘除，并且旧实例报告自进入排空以来最后一次接纳新请求的时间之后连续一段时间没有新的接纳。排空期间仍到达的请求照常处理 |
| X2 | 旧实例的在途请求归零 | 在途数为 0，包括流式、非流式和它正在执行的批处理条目 |
| X3 | 计费和日志收尾完成 | 请求日志队列为空且没有正在进行的写入；费用账本 `unwritten()` 为零；搁置条目数单独报告（它们不会再被写入，必须出现在发布记录里） |

网关给每个请求设了上限（`REQUEST_TIMEOUT_SECONDS`、`STREAM_REQUEST_TIMEOUT_SECONDS`，后者默认 3600 秒），所以 X2 正常一定会在这个上限内满足，旧实例最长可以存在一个流上限那么久，期间新实例已在服务。排空必须发生在停止信号之前，由发布编排发起并确认，因为下面的异常处理都需要实例还活着、还能回到服务。

### 4.3 网关一侧（已实现）

网关提供 `/internal/handoff`（`GET` 状态，`POST` 的 `drain`、`seal`、`resume`），用进程环境变量 `HANDOFF_TOKEN` 授权，没有这个变量时接口不存在。不用管理凭据，是因为要求管理员第二重验证的部署里管理令牌对修改是只读的。接口、`blocking` 原因和发布顺序见[部署指南](../../developer/deployment.md#handing-traffic-to-a-new-gateway-process)。设计上的几个要点：

- 封口（seal）是检查加切换的一步：排空中的进程只有在没有在途请求、没有后续工作、没有打开的客户端连接（发布调用和探活除外）、X3 已确认入账时才能封口，否则返回 409 并保持排空。封口后到达的请求在做任何事之前被拒绝（503，`instance_sealed`）并计数，这个数不为零就不能记为无损。这样“刚查到为零又来了请求”不会被截断，而是被如实记下。
- X3 按“已确认入账”判定，不是“没有正在执行的写入”。结果未知或被计数表拒收的费用、被隔离或无法核对的预留、写入失败或被丢弃的请求日志行、收尾超时被中断的流，都让封口返回 409，且不会自行消失。没有强制封口的例外。
- “请求结束”包括它留下的后续工作：流的关闭、被拒请求的日志行、Responses 的保存、告警发送、费用写入。批处理条目要等任务结束才算完成。
- 排空中的进程仍处理到达的请求，`/health/ready` 返回 503 并说明排空（`/health` 仍是 200），不再领取批处理条目，不跑定时任务。停止信号的行为不变。

### 4.4 发布编排与异常处理（发行版，未实现）

正常顺序：新实例就绪并通过验收 → 入口摘除旧实例 → 旧实例排空 → 确认 X1 到 X3 → 停止旧实例。

超过预期时限即为异常。异常不自动处理，由发布负责人选择并记录：

| 异常 | 保留实例 | 中止发布 | 强制终止 |
|---|---|---|---|
| X1 不满足，旧实例仍收到新请求 | 旧实例继续服务，发布暂停，排查入口 | 旧实例退出排空回到入口，撤下新实例 | 不允许，会打断新请求 |
| X2 不满足，请求超过网关上限仍未结束 | 旧实例继续存在，记为“未完成” | 不适用 | 允许，先记录将被打断的请求清单 |
| X3 不满足，日志或费用写不进去 | 默认选择，停止会丢内存里的费用和日志 | 不适用 | 允许，先记录将丢失的金额和条数 |
| 新实例在旧实例排空期间出问题 | | 旧实例退出排空回到入口，撤下新实例（只在旧实例尚未停止时可行，这是排空先于停止的原因） | |

发布结果有四种：无损成功（X1 到 X3 在停止前全部确认，停止时在途为 0、未写入为 0、无搁置条目）、有损完成（强制终止，或停止时仍有在途请求、未写入费用或搁置条目，附数量）、中止、未完成。强制终止和任何停止时在途数不为 0 的发布，都不能记为无损成功。

### 4.5 设计门槛：并存期间的限额与封禁（未通过）

下面的状态都在进程内，并存期间新实例看不到旧实例上的部分。这是阶段二进入实现之前必须逐类给出结论并通过评审的分析：证明偏差在明确上界内且可接受，或改为跨进程可见，或限制发布形态。

并存有两种形态：旧实例已摘除、只做完在途请求（排空期），以及滚动替换时新旧实例同时接纳新请求（重叠期）。另需部署侧先确认今天是否已经在跑多于一个网关实例，如果是，下面的缺口现在就存在。

| 类别 | 状态 | 偏差 |
|---|---|---|
| 并发 | 每用户、每项目的并发上限（`serving/servers/concurrency.py`） | 排空期最坏是上限的两倍，重叠期随同时接纳的实例数放大，随旧请求结束自行恢复 |
| 并发 | 对上游的并发上限（AIMD，不持久化） | 新实例从初始值重学，一直放行到上游返回 429，没有固定上界 |
| 并发 | RouteWise 配额与并发、FixedRouter 预填充负载 | 只影响路由选择质量，不是额度 |
| 并发 | 批处理的模型并发 | 在数据库，跨进程，无偏差 |
| 费用 | 旧实例上在途请求的费用 | 预留的是估算值，实际值到结束才知道，一个长流可以远超估算。上界是这些请求各自最大可能费用之和，不是在途请求数 |
| 费用 | 旧实例上已结束但还没写进计数表的费用 | 数据库健康时很小；写入失败时累积，没有上界，直到写入恢复或实例退出 |
| 费用 | 计数表拒收而搁置的条目 | 永久不计入额度，只能靠上报发现 |
| 限流 | 登录、注册限流（进程内字典） | 实际阈值是配置值乘以同时接纳的实例数；排空期新实例等于计数清零 |
| 封禁 | 鉴权失败封禁（进程内字典，重启即丢） | 被封的来源在新实例上重新获得整个阈值；管理员解除封禁只作用于应答的那个进程 |

并存让“看不到的金额”比今天的重启更大：今天重启时在途请求 5 秒后被取消并停止产生费用，并存之后这些请求继续跑，而新实例在它们落表之前不知道。费用预算最需要先解决，因为偏差是钱，且在数据库不健康时没有上界。已有的跨进程做法可以参考：每个进程定期把在途数发布到数据库（`serving/batch/interactive_load.py`）。

并存期间每用户并发最坏是上限的两倍，定时上报占用不能把它变成严格上限，要严格上限需要跨进程的原子名额，单独评审。

### 4.6 其他并存约束

| # | 约束 |
|---|---|
| C1 | 数据库结构：迁移在新实例启动前执行，旧代码必须能在新结构上工作，先扩展后收缩的规则已覆盖 |
| C2 | 配置：新旧实例读同一份数据库配置，并存期间保存的内容旧实例必须读得懂或安全忽略。改变已存配置格式的发布要像结构变更一样分两个版本做。旧版本对未知字段的处理要逐类核实 |
| C3 | 后台任务：排空中的实例不再领取新工作。批处理按租约设计，可由新实例接手。告警评估、邮件调度、价格同步等没有按多进程设计的任务不能重复触发，实现前要列出全部后台任务逐个核对 |
| C4 | 重叠期同一个客户端的连续请求可能先后落在新旧版本上，相邻两个发布在 API 行为上必须能这样交替 |
| C5 | 回滚时旧镜像启动、新镜像排空，约束与正向相同，兼容下限的检查决定旧镜像能否启动 |

## 5. 验收与回滚

探针脚本 `ops/dev/entry_split_probe.py` 从外部运行：用原始 HTTP 客户端、不重试，每次失败都计数；长流记录每帧到达时间、用带序号的合成上游逐帧核对内容，并检查结束标记和 usage；按固定速率持续发出短的流式和非流式请求，覆盖 `/v1/chat/completions`、`/v1/responses`、`/anthropic/v1/messages`；健康检查只作辅助信号。合成上游（example 的假模型服务）可设帧间隔。

阶段一场景，每个开始前先起一批覆盖整个操作的长流，同时保持新请求的固定速率：

| # | 操作 | 说明 |
|---|---|---|
| S1 | 发布新的控制台镜像 | 主场景 |
| S2 | 强制结束控制台进程 | 模拟崩溃 |
| S3 | 控制台完全停止 60 秒后恢复 | 最强的独立性证明，也检查 3.1 节 |
| S4 | 撤掉分流规则再加回来 | 验证回滚。是否打断经入口的在途流取决于入口，要如实记录 |
| S0 | 对照：在原路径上重复 S2 | 会打断所有经控制台的推理请求，探针必须报告流被打断，测不出失败的测试不能证明通过 |

S0、S2 到 S4 是故障注入，会影响 staging 的其他使用者，要事先通知并单独安排窗口，S0 影响最大，单独排一个。

通过标准：

- S1 到 S3 没有长流被打断或内容不完整，新请求失败数为 0（窗口外本来有偶发失败的，以同样时长的基线为准）。
- 每个长流在 `api_logs` 有一行，usage 完整，费用已记入。
- 网关日志的 `peer_ip` 与入口访问日志都显示请求由入口直接送达。
- S3 和 S1 期间网关就绪不变、身份解析不变，不需要重启网关。
- S0 确实测出失败，第 3 节的检查全部通过，已知变化与列出的一致。

阶段二用同一个探针，把操作换成后端发布，只有“无损成功”算通过，并要求并存期间没有重复的后台任务，且 4.5 节选定的方案各有对应检查。

回滚：撤掉入口上的两条规则，流量回到控制台的内置转发，不需要回退镜像。前提是控制台镜像保留转发、网关对控制台的信任配置保留、前端的停止宽限时间没有缩短。触发条件：分流路径的错误率高于基线；客户端身份 `unknown` 的比例上升；网关就绪因前端变化而抖动；出现第 3 节以外的行为差异。

## 6. latency 对照实验

要回答绕过控制台后端到端 latency 有没有可测量的变化、在哪些条件下有、对用户有没有意义。结果不决定是否分流，除非分流路径出现回退。

**两条路径同时可达。**

- 外层：同一个入口上配两个主机名，一个把所有路径交给控制台（原路径），一个启用分流。同一台客户端、同一时间段交替发请求（ABBA）。
- 内层：从同一网络内部直接请求控制台的 `/v1` 和网关的 `/v1`，量出控制台这一跳的开销。
- A/A 校准：正式比较前两个主机名都指向原路径跑一遍，两边的差是噪声底。
- 每个请求按路径证明抽查。

**变量控制。**

| 变量 | 做法 |
|---|---|
| 模型与上游波动 | 主要结论用合成上游（固定首字延迟、帧数、帧间隔、帧大小），另用一个真实模型确认趋势 |
| 输出长度 | 合成上游固定；真实模型固定 `max_tokens`、`temperature=0`，事后核对 `completion_tokens` 相同，不同的样本剔除并报告数量 |
| 缓存 | 前缀每次相同和前缀带随机串两组，分别报告 |
| 路由 | 同一个 API key，记录每个请求落到的 endpoint，按 endpoint 分层比较 |
| 请求体 | 约 1 KB 和约 1 MB 各一组（原路径上请求体要经过 Node） |
| 客户端与网络 | 同一台机器、同一时间段、交替发送，连接复用策略两边相同 |

**指标。** TTFT（到第一个带内容的事件，保活注释不算）、流内相邻帧间隔（合成上游下减去发出间隔得到路径抖动）、整请求耗时（减去网关 `duration_ms` 得到路径开销）、错误（非 2xx、传输错误、被截断的流分别计数，失败请求不进 latency 统计）。报告 P50、P95、P99 和两路径之差的置信区间；每个场景每条路径至少 1000 个请求，少于 2000 个不报告 P99。

**场景。** 低并发（1 个请求）；正常负载（取该部署实测的常态和高峰并发）；网页服务有负载（在正常负载之上另一个发生器以固定速率请求控制台页面，新路径不应受影响）；压力（可选，常态 10 倍）。后两个会让 staging 网页变慢，也要安排窗口。

**判读。** 下面的阈值是候选值，评审确认后冻结，冻结之后才跑 A/B，看到数据后不再修改。

第一层，统计上有没有差别：两路径之差的 95% 置信区间（按交替配对自助法）不含 0，并且差的绝对值大于噪声底（A/A 校准中同一指标两边之差的 95% 置信区间两端绝对值较大者）。不满足时结论是“没有可测量的差别”，这是合法结论。

第二层，业务意义（统计上有差别之后才看，绝对值与相对值取较大者）：

| 指标 | 候选阈值 |
|---|---|
| TTFT P50 | 20 毫秒，或基线的 5% |
| TTFT P95、P99 | 50 毫秒，或基线的 10% |
| 路径引入的帧间抖动 P99 | 50 毫秒（入口缓冲了响应只会在这个指标上表现出来） |
| 路径开销 P50 / P95 | 20 毫秒 / 50 毫秒（固定附加量，只用绝对值，相对整个请求通常不到 1%，结论里照实写） |
| 大请求体上传耗时 P50 | 50 毫秒 |

每个指标的结论是四种之一：没有可测量的差别；可测量但低于业务阈值；有业务意义的改善；回退。分流路径在任一场景任一指标上比原路径差且超过业务阈值就是回退，查清原因并重测之前不推进到生产（它少一跳，没有理由更慢，通常意味着入口配置有问题，例如缓冲）。

错误率单独设门槛：路径造成的错误（入口自己返回的 5xx、连接被重置、流被截断，而网关日志显示该请求成功或根本没收到）在分流路径上为 0，每条路径累计不少于 3000 个请求，出现任何一次都查明原因并整组重跑；总错误率分流路径不高于原路径，差值不超过 A/A 校准中两边的差；任一场景失败请求超过 1% 时该场景结果作废重跑。

结果连同原始数据位置、两条路径的配置和冻结的阈值，写成带日期的记录。发行版的主机名和账号不写进本仓库。
