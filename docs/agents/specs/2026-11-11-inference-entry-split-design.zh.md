## 1. 背景

### 1.1 当前请求路径（基于 `dev` @ `7e1ea5c8f`）

```text
客户端 / SDK ─▶ 入口（CDN、隧道或负载均衡，由发行版提供）
                  │  所有路径
                  ▼
            Next.js 控制台 ─┬─▶ 网关（/v1、/anthropic、/auth、/user、/admin、已公开的 /internal …）
                            └─▶ 自己的页面
                                   网关 ─▶ 模型服务
```

控制台有两个职责：提供网页，以及转发推理 API。一次长时间的流式请求要经过两个都会被发布的进程
（控制台、网关），任何一个重启都会打断它。

### 1.3 没有测量过的

- **前端发布和后端发布各自造成多少中断，没有数据。** 第 1 版用提交占比（最近 300 个 `dev` 提交里只改前端 46 个、
  只改后端 125 个、两边都改 82 个）推断停机的来源，这个推断不成立，已删除：提交不等于发布；一次发布可能
  同时重启两个服务而不管改了什么（F25）；一次重启打断多少请求取决于当时的在途流，与改动无关。
  这组数字只说明代码改动的分布。
- 需要的数据是：每次发布实际重启了哪些服务，以及当次被打断的请求数。步骤 0（§10）负责取得它。
- 两组旧的实测只作量级参考，实施前重测：2026-10-19 一个 Compose 部署的 staging 上，一次发布 API 不可用
  23.4 秒（后端停止 7.5 秒、前端停止 10.4 秒、后端启动约 5 秒，测于 #1756 之前）；同日一个生产部署 30 天的
  流式请求耗时 P99.9 为 198 秒、最长 3618 秒。**后者不作为截断流的依据**（§6.2）。

| # | 假设 | 不成立时 |
|---|---|---|
| H1 | 发行版现有的入口能按路径把 `/v1`、`/anthropic` 交给网关，其余路径不受影响 | 该发行版留在内置转发，不做分流 |
| H2 | 入口对这两个前缀不缓冲响应，空闲超时不短于网关的限制，客户端断开会传到网关 | 调整入口配置；调不了则不做分流 |

| H7 | 绕过控制台对 latency 的影响：低并发下差别很小；网页服务有负载时，经控制台的尾部延迟更差 | 只影响目标二的结论，不影响分流本身 |
| H8 | 网关在入口后面给出的尾斜杠重定向地址是对的 | 网关侧修正后才能上线 |

### 1.5 预期收益

在 H1、H4、H5 成立的前提下，阶段一带来：

- 网页的发布、重启和故障不再影响推理请求。
- 长流少经过一个会被发布的进程。
- 前端旧实例的等待时间不再需要覆盖最长的流，只需覆盖网页和短的浏览器请求。
- 推理请求的排查少一跳。

这些收益有多大没有量化，取决于 §1.3 缺的那组数据。

不在阶段一的收益里的：

- 后端发布造成的中断。它与分流无关，属于阶段二。阶段二完成之前，每次后端发布仍会打断超过 5 秒的流。
- latency。是否有改善由 §9 的实验回答，本文不预设结论。
- 更简单的信任配置。阶段一网关有两个合法的对端（控制台和入口），配置比现在多一项。

## 2. 目标与非目标

目标：

1. 推理 API 与网页发布解耦：网页发布期间，已开始的推理请求完整结束，新的推理请求正常成功。
2. 用对照实验回答"绕过 Next.js 是否改善端到端 latency"，结论可以是"没有明显差别"。
3. 给出后端并存发布的设计（阶段二）：新实例接新请求，旧实例做完已有请求、写完计费和日志后退出；
   并列出进入实现之前必须通过的门槛。

非目标：

- 改变对外地址。域名、API 地址和各前缀都不变。
- 移动 `/v1`、`/anthropic` 以外的任何接口。`/auth`、`/user`、`/admin`、`/internal/*`、`/health`、
  `/site-config` 等保持经控制台转发。浏览器里的 playground 长流（`/internal/playground`）因此仍经控制台，
  这是本阶段接受的遗留。
- 删除内置转发。它是默认拓扑，也是分流的回滚目标。
- 增加独立的代理服务，或把 nginx 加回来（#1444）。分流只用发行版已有的入口。
- 为了分流放宽网关的全局信任（§5.2）。
- **自带 Compose 部署的新旧后端并存。本期不做**；Compose 部署本期只获得入口分流的收益，
  后端发布仍按现状打断请求。
- 跨服务器切换。

## 3. 目标请求路径

```text
客户端 / SDK ─▶ 入口（同一个域名）
                  ├─ /v1、/anthropic ───────────────▶ 网关 ─▶ 模型服务
                  └─ 其余路径 ─▶ Next.js 控制台 ─┬─▶ 网关（浏览器接口，保持现状）
                                                 └─▶ 自己的页面
```

核心同时支持两种拓扑，对外行为必须一致（§5），用同一套检查验证：

| 拓扑 | 谁把 `/v1`、`/anthropic` 交给网关 | 用在哪里 |
|---|---|---|
| 内置转发（默认，现状） | 控制台的 route handler | example、本地、单端口部署、入口不能按路径分流的部署 |
| 入口分流（发行版选择启用） | 发行版的入口 | 入口能按路径分流的部署，例如 Kubernetes Ingress 的路径规则或隧道的路径路由 |

启用入口分流的部署里，控制台镜像不变，它的 `/v1`、`/anthropic` 转发仍然存在。正常情况下没有公网流量
走到它；撤掉入口规则后流量自动回到它。

## 4. 职责划分

### 4.1 核心负责

- 公开路径清单（§4.3），以及让内置转发与清单一致的测试。
- 内置转发本身，作为默认拓扑继续维护。
- 网关在两种拓扑下行为一致：凡是现在由控制台顺带提供、分流后会丢失的行为，在网关侧补齐（§5）。
- 一份入口约定：分流路径上入口必须满足的条件（§4.2 的表），写进 `docs/developer/deployment.md`。
- 一个从外部验证的探针脚本（§8.1），发行版在自己的 staging 上运行。
- 阶段二里网关进程的排空接口和停止约定（§6.3）。

### 4.2 发行版负责

- 决定是否启用入口分流，并在自己的入口上配置规则。核心不提供任何入口配置文件。
- 提供入口能力和实际信任配置的实测证据（H1、H2、H4、H5、H6）。
- 分流路径上，入口满足下面的约定：

| # | 入口约定 |
|---|---|
| E1 | 只把清单里标记可分流的前缀交给网关：路径等于 `/v1`、`/anthropic`，或以 `/v1/`、`/anthropic/` 开头。匹配在解析完 `.`、`..` 和百分号编码之后进行 |
| E2 | 不缓冲响应，也不把请求体整份读完再转发 |
| E3 | 空闲超时大于网关的 `REQUEST_TIMEOUT_SECONDS`；不设短于 `STREAM_REQUEST_TIMEOUT_SECONDS` 的总时长上限。流每 15 秒有一次保活 |
| E4 | 请求体上限不低于网关自己的上限（含 `/v1` 下的文件上传） |
| E5 | 客户端断开时，关闭到网关的请求 |
| E6 | 覆盖客户端送来的来源头（`X-Forwarded-For` 或 `CF-Connecting-IP`） |
| E7 | 网关端口只有入口和控制台能连到 |
| E8 | 请求已经发给网关之后，不自动重发 `POST`。连接没建立成功时可以换一个实例重试 |
| E9 | 实例被摘除时：停止向它分配新请求，但不关闭它上面已建立的连接（阶段二需要） |

- 网关对入口的信任按 §5.2 配置。
- 在自己的 staging 上跑完 §8 的验收和 §9 的实验，保留结果。
- 发布编排：先后顺序、新旧实例并存的方式、各个决定点由谁判断（§6.4）。

### 4.3 统一的公开路径清单

现在的约定是"控制台拥有公开路径表"，清单写在四处（F4）。入口分流以后，入口规则是第五处。
为了不让它们各自漂移，核心新增一份机器可读的清单，作为唯一来源：

```json
{
  "version": 1,
  "paths": [
    { "path": "/v1",        "match": "prefix", "owner": "gateway", "entry_split": true  },
    { "path": "/anthropic", "match": "prefix", "owner": "gateway", "entry_split": true  },
    { "path": "/auth",      "match": "prefix", "owner": "gateway", "entry_split": false },
    { "path": "/internal/verify-admin", "match": "exact", "owner": "gateway", "entry_split": false },
    { "path": "/health",    "match": "exact",  "owner": "gateway", "entry_split": false }
  ]
}
```

（示意，完整内容照搬 `public-path-table.md` 现有的表。）

- 文件放在 `deploy/public-paths.json`。它描述的是部署对外的面，前端测试、文档和发行版都读它。
- `match: "prefix"` 的含义与 `gatewayProxy.ts` 的 `isUnder` 相同：路径等于该前缀，或以该前缀加 `/` 开头，
  判断在解析完点号段之后进行。
- `entry_split: true` 表示入口可以把它直接交给网关。本文只把 `/v1` 和 `/anthropic` 标为 `true`。
  以后要多分一个前缀，改的是这一个字段，并重新走 §8 的验收。
- 清单里没有的网关路径不得从公网到达。清单里没有的其他路径归控制台。

使用方：

1. 前端测试。`gatewayRoutes.test.ts` 里手写的路由列表、`middleware.ts` 的 matcher、`redirects()` 的正则、
   `rewrites()` 各自与清单比对，不一致时测试失败。matcher 仍然是字面量字符串（Next 在构建时读取，不能计算），
   由测试保证它和清单一致。
2. 文档。`public-path-table.md` 改为：清单是来源，控制台是默认实现，入口可以实现标记了 `entry_split` 的部分。
   "发布新路径不需要改入口"改为"分流前缀之外的新路径不需要改入口"。
3. 探针脚本（§8.1）。它读清单，从外部检查：可分流的前缀到了网关，清单以外的网关路径到不了。

核心不生成入口配置。两条规则由发行版手写，探针负责发现写错。

### 4.4 example 与本地

不变。example、`make up`、本地开发继续用内置转发，一个端口、同源、不需要任何入口。
两种拓扑共用网关和控制台的同一份镜像，区别只在入口有没有那两条规则。

## 5. 必须保留的行为

### 5.1 行为对照

每一行都是对外可观察的行为。"分流后"一列说明由谁保证，"检查"一列对应探针里的一项。

| 行为 | 现在 | 分流后 | 检查 |
|---|---|---|---|
| 鉴权 | 网关校验 API key；控制台不参与（F1） | 不变 | 无 key、错 key、被停用的 key 各返回与原路径相同的状态码和错误体 |
| 公开路径边界 | 控制台只转发清单里的路径；`isUnder` 拒绝越界（F3、F5） | 入口 E1、E7；探针从外部验证 | `/docs`、`/redoc`、`/openapi.json`、`/health/deep`、未公开的 `/internal/x`、`/v1/%2e%2e/openapi.json`、`/v1/../openapi.json`、`//v1` 等都拿不到网关的未公开内容（H3） |
| 流式输出 | 逐字节转发，不缓冲（F2） | 入口 E2 | 合成上游按固定间隔发出带序号的帧，客户端收到的间隔与发出的一致，序号不缺不重 |
| 客户端取消 | 调用方挂断，网关请求立刻取消（F2） | 入口 E5 | 客户端中途断开后，网关日志在限定时间内记录该请求被取消，上游连接关闭 |

| 请求体大小 | 网关拒绝超限的请求体；控制台流式转发、不留存 | 入口 E4 | 略低于上限的请求体成功；超限时返回 413 |
| 错误响应 | 网关的错误体原样返回。网关连不上时，控制台回 OpenAI 格式的 JSON 502 / 504（F2） | 网关的错误体不变。网关连不上时由入口回 502 / 503 / 504，**响应体是入口自己的**，不保证是 JSON | 状态码必须正确。响应体的差异是已知变化，写进发布说明；发行版可以在入口上配置 JSON 错误体 |
| 客户端 IP 与就绪 | 取决于对控制台的信任配置（F8） | 见 §5.2 | 见 §5.2 |
| 尾斜杠 | `redirects()` 把 `/v1/models/` 改写到 `/v1/models`（F6） | 网关侧保证（H8）：实现前先测网关直接给出的重定向，不对就在网关修 | `/v1/models/` 的结果与原路径相同，`Location` 不含内部地址，协议正确 |
| 安全响应头 | 控制台加三个头（F6） | 网关自己给响应加 `X-Content-Type-Options: nosniff`。另外两个头只对网页有意义，分流路径上不再出现 | 分流路径的响应带 `nosniff`。少两个头是已知变化 |
| 同源、cookie、CORS | 浏览器看到同一个域名 | 不变，域名和路径都没变 | 控制台的聊天页面在分流开启后照常工作 |

**路径证明。** 判断一个请求走了哪条路径，依据是网关请求日志里的 `peer_ip`（已有字段）和入口自己的访问日志，
两者对得上才算证明。内置转发可以另加一个标准的 `Via` 响应头方便排查，这是可选项：它不是分流的前置条件，
也不能单独作为路径证明（响应头可以被中间层改写）。

### 5.2 入口直连时的身份与就绪

分流的目标是推理不依赖前端。所以下面两条必须在**前端全部停止**时仍然成立：

- **身份**：经入口直连的请求，客户端身份照常解析，结果与原路径相同。
- **就绪**：网关的 `/health/ready` 保持通过，入口不会因此把网关摘掉。

约束：**不为分流放宽全局信任。** 具体是不做下面任何一件：关闭 `TRUST_PROXY_HEADERS`；把一个包含其他工作负载的
网段加进信任列表；在代理发现模式下恢复静态列表作为回退；把 `unknown` 身份当作正常结果放行。

按部署现在的信任方式分两种情况。

**静态信任（未启用代理发现）。** 就绪不依赖代理（F12），前端停止不影响它。身份方面，把入口在网关眼中的
精确对端地址加入对应的信任项（入口写 `X-Forwarded-For` 的加入 `TRUSTED_PROXIES`，Cloudflare 的加入
`TRUSTED_CLOUDFLARE_NETWORKS`），控制台的地址保留。加入的范围只能是入口自己；如果入口的对端地址与其他进程
无法区分（例如同机回环端口映射后，所有本机进程在网关眼中是同一个地址），该部署需要先解决这一点，
不能用"信任这个共用地址"代替。

**代理发现模式。** 按今天的实现，分流在这种部署上达不到目标，原因有三个，都已核实：

1. 入口不在被发现的那个 Service 里，经入口直连的请求身份全部是 `unknown`（F9）。
2. 前端全部停止时成员为空，`/health/ready` 返回 503（F10），入口随即摘掉网关。前端停止因此直接造成推理中断，
   正是本文要消除的那种耦合。
3. 前端用 Deployment 时，前端每次发布都要求改 UID 并重启网关（F11）；阶段二完成之前，重启网关就是打断推理。

要在这种部署上启用分流，核心需要先满足下面的要求。这是一项核心改动，只在第一个发行版确实使用该模式时
进入最小范围（§11 的问题 2）：

| # | 要求 |
|---|---|
| T1 | 入口是一个**独立命名的信任来源**，与前端来源分开配置，校验强度不低于现有来源：精确地址、固定的身份标识、快照有时效、读取失败时不给信任 |
| T2 | 每个请求的身份只由它的实际对端所属的来源决定。前端来源为空或失效，不影响入口来源的请求；反之亦然。不属于任何来源的对端仍然是 `unknown` |
| T3 | 就绪由"能把流量直接送到网关的来源"决定：入口来源非空且未过期时通过，不要求前端来源非空。前端来源为空或失效要在 `/health/ready` 的响应体和告警里报告，但不改变就绪结果 |
| T4 | 来源的身份标识在该来源正常发布后保持有效，不需要重启网关。前端来源同样需要满足，否则原因 3 仍然存在 |
| T5 | 入口不是 Pod（例如云负载均衡直连）时，Pod 发现不适用。需要一种同样精确、同样会失效的来源形式，具体方案等部署侧的证据 |

T3 相对现状的变化是：前端来源失效时网关不再整体退出服务，而是只让来自前端的请求身份变成 `unknown`
（沿用现有的未解析身份处理）。这不是放宽信任——没有任何新的对端被信任——但它改变了失效时的表现，
需要评审确认。

检查（§8 的 S3 和 S1 覆盖）：前端全部停止期间，每个网关实例的 `/health/ready` 一直通过；经入口的请求
`ip_resolved` 为真、`remote_ip` 与停止前一致；从入口以外的对端直连网关并带伪造的来源头，身份是 `unknown`。
前端发布全程不需要重启网关，就绪不抖动。

## 6. 后端并存发布（阶段二）

本阶段与分流互不依赖，单独评审、单独发布，本期不进入实现。放在分流之后的原因是：分流之后推理请求在网关
前面只有入口，不必再处理控制台转发在后端换实例时的连接复用问题（F2：失败不重试）。

### 6.1 现状

网关收到停止信号后 5 秒取消所有请求（F13），所以每次后端发布都会打断超过 5 秒的流。把 5 秒直接调大没有用：
单个实例停止接受连接之后，新请求在整个等待期间都失败。

**单实例部署保持现状**：收到停止信号后 5 秒取消、落盘、退出，行为和默认值都不变。这是一次有损的重启，
它打断了多少请求要写进日志（§6.4 的"有损"记录同样适用）。下面的排空策略只用于新旧实例并存的部署，
是独立的一条路径，不通过调大那个 5 秒来实现。

### 6.2 正常发布的退出条件

旧实例只有在下面三个条件**全部确认**之后才被停止。条件是状态，不是时间：

| # | 条件 | 怎么确认 |
|---|---|---|
| X1 | 入口已停止向旧实例分配新请求 | 入口侧显示该实例已摘除；并且旧实例报告"自进入排空以来，最后一次接纳新请求的时间"之后连续一段时间没有新的接纳。排空期间仍然到达的请求照常处理、不拒绝，但只要还有新请求到达，X1 就没有满足 |
| X2 | 旧实例的在途请求归零 | 旧实例报告在途数为 0，包括流式、非流式，以及由它正在执行的批处理条目 |
| X3 | 计费和日志收尾完成 | 请求日志队列为空且没有正在进行的写入；费用账本 `unwritten()` 为零；搁置条目数单独报告（它们不会再被写入，必须出现在发布记录里，不能被"为零"掩盖） |

不按历史分位数截断长流。网关自己给每个请求设了上限（`REQUEST_TIMEOUT_SECONDS`、
`STREAM_REQUEST_TIMEOUT_SECONDS`，后者默认 3600 秒），所以 X2 在正常情况下一定会在这个上限之内满足；
这意味着一次正常发布里，旧实例最长可以存在到流的上限那么久，期间新实例已经在服务。

这要求排空发生在**停止信号之前**，由发布编排发起并确认，而不是进程收到停止信号之后自己计时。
原因是 §6.4 的三种处理都需要实例还活着、还能回到服务。

### 6.3 网关进程提供的（核心）

只列对外约定，实现细节留给实现计划。

- **进入排空**：一个不在公开路径清单里、需要管理凭据的操作。进入后 `/health/ready` 返回 503 并说明原因是排空，
  `/health` 仍返回 200 并带排空状态。排空期间到达的请求照常处理。实例停止领取新的后台工作（批处理不再认领新条目）。
- **退出排空**：实例回到正常服务，`/health/ready` 恢复，后台工作恢复。用于中止发布。
- **排空状态**：报告 X1、X2、X3 需要的数字——最后一次接纳新请求的时间、在途数（分类型）、
  日志队列深度、未写入的费用金额和请求数、搁置条目数——以及实例 id 和版本（F23）。
- **停止**：收到停止信号时的行为不变（5 秒、落盘、退出）。对一个已经满足 X1 到 X3 的实例，这一步不打断任何请求。
  进程在退出前把"停止时仍在途的请求数"和"未写入的费用"写进日志，供发布记录使用。
- 请求日志带实例 id，能分辨每个请求由哪个实例、哪个版本处理。

### 6.4 发布编排与异常处理（发行版）

正常顺序：新实例就绪并通过验收 → 入口摘除旧实例 → 旧实例进入排空 → 确认 X1、X2、X3 → 停止旧实例。

每个条件都有一个预期时限，超过即为异常。异常不自动处理，由发布负责人在下面三种里选择，并记录选择和原因：

| 异常 | 预期时限 | 保留实例 | 中止发布 | 强制终止 |
|---|---|---|---|---|
| X1 不满足：旧实例仍在收到新请求 | 入口的摘除生效时间（由部署实测给出） | 旧实例继续服务这些请求；发布暂停，排查入口 | 旧实例退出排空、回到入口；新实例撤下 | **不允许**。此时终止会打断新请求 |
| X2 不满足：有请求超过了网关自己的上限仍未结束 | 流的上限加余量 | 旧实例继续存在，发布记为"未完成"，排查卡住的请求 | 不适用（新实例已在服务；是否回退新版本是另一个决定） | 允许，但必须先记录将被打断的请求清单 |
| X3 不满足：日志或费用写不进去（例如数据库不可用） | 写入重试的上限加余量 | 默认选择。实例停止就会丢失还在内存里的费用和日志 | 不适用 | 允许，但必须先记录将丢失的金额和条数 |
| 新实例在旧实例排空期间出问题 | — | — | 旧实例退出排空、回到入口；新实例撤下。只有旧实例尚未停止时可行，这是排空必须先于停止的原因 | — |

发布结果只有四种，必须如实记录：

| 结果 | 含义 |
|---|---|
| 无损成功 | X1、X2、X3 全部在停止之前确认，停止时在途数为 0、未写入为 0、无搁置条目 |
| 有损完成 | 发生过强制终止，或停止时仍有在途请求、未写入的费用或搁置条目。附被打断的请求数和未写入的金额 |
| 中止 | 回到旧版本 |
| 未完成 | 旧实例被保留，发布没有结束 |

**强制终止、以及任何停止时在途数不为 0 的发布，都不能记为无损成功。**

### 6.5 设计门槛：新旧并存期间的限额与封禁

第 1 版把这部分统称"进程内限额"，用"切换时的在途请求数"作为风险上界，并建议接受。这个结论不成立，
**未获批准**。下面按类别拆开。这是阶段二进入实现之前必须完成并通过评审的分析，不阻塞阶段一。

并存有两种形态，风险不同：旧实例已摘除、只做完在途请求（下称"排空期"）；滚动替换多个副本时新旧实例
同时接纳新请求（下称"重叠期"）。另外要先由部署侧确认一件事：今天是否已经在跑多于一个网关实例。
如果是，下面的缺口现在就持续存在，阶段二只是延长了它，而不是引入它。

**（一）并发限制**

| 状态 | 在哪里 | 并存期间新实例看不到什么 | 上界 | 是否自行恢复 |
|---|---|---|---|---|
| 每用户、每项目、每组织的并发上限（F17） | 进程内计数 | 同一用户在旧实例上还在跑的请求 | 排空期：该用户在旧实例上的在途数，不超过他的上限，所以最坏是上限的两倍。重叠期：每多一个同时接纳的实例多一倍 | 是，随旧请求结束 |
| 对上游的并发上限（F19） | 进程内学习值，不持久化 | 旧实例对同一个提供方账号仍占用的并发；新实例的学习值从初始值重新开始 | 没有固定上界：新实例会一直放行到上游返回 429，再逐步降下来 | 是，但靠 429 纠正，期间用户会看到排队或失败 |
| RouteWise 配额与并发、FixedRouter 预填充负载（F20） | 进程内 | 旧实例上的在途负载 | 影响的是路由选择的质量（可能把请求分到其实很忙的端点），不是额度 | 是 |
| 批处理的模型并发上限 | 数据库，跨进程（F22） | 无 | 无偏差 | — |

**（二）费用预算**

额度判定读数据库里的计数表，再加上本进程账本里还没进表的部分（F16）。另一个实例账本里的部分看不到。
这里有三类，不能合并成一个数：

| 看不到的部分 | 大小由什么决定 | 上界 |
|---|---|---|
| 旧实例上在途请求的费用 | 这些请求最终的实际费用。预留的是估算值，实际值到请求结束才知道，一个长流可以远超估算 | 不是"在途请求数"。上界是这些请求各自的最大可能费用之和，受每用户并发上限和单请求的最大输出约束 |
| 旧实例上已结束但还没写进计数表的费用 | 正常时很小、很快清空。数据库写入失败时会一直累积，重试退避最长 30 秒 | 数据库健康时很小；不健康时没有上界，直到写入恢复或实例退出 |
| 计数表拒收而搁置的条目 | 不会再被写入 | 永久不计入额度，只能靠上报发现 |

方向上，排空期只有"新实例看不到旧实例"这一个方向（旧实例不再接纳）。重叠期两个方向都有，
一个用户可以同时在两边各用到接近上限。

与今天的重启相比：今天重启时在途请求在 5 秒后被取消并停止产生费用（#1756 的说明是被中断的请求照常计费，
停止时的落盘是否覆盖全部情况要在实现前核实）；并存之后这些请求继续跑、继续产生费用，而新实例在它们落表
之前不知道。所以并存让"看不到的金额"比今天更大，这是第 1 版漏掉的。

另有一类不影响额度但影响账单的：`api_logs` 的写入队列有界，满了丢最旧的（F15）。排空期旧实例只剩写入、
没有新请求，这个风险不变；它由 X3 的队列深度覆盖。

**（三）限流**

| 状态 | 在哪里 | 并存期间 | 上界 |
|---|---|---|---|
| 登录限流（按账号加地址、按账号、按地址）、注册限流（F21） | 进程内字典 | 这些接口不在分流范围内，仍经控制台到网关。重叠期一个来源的尝试分散到各实例，每个实例单独计数 | 实际阈值是配置值乘以同时接纳的实例数。排空期旧实例不再接纳，新实例从零开始，等于一次计数清零 |
| 按请求数的 API 限流 | 没有找到；`/v1` 上的 `X-RateLimit-*` 头表达的是费用额度 | — | 归入（二） |

**（四）封禁状态**

| 状态 | 在哪里 | 并存期间 | 后果 |
|---|---|---|---|
| 鉴权失败封禁（F21） | 进程内字典，重启即丢 | 旧实例上已生效的封禁，新实例不知道；被封的来源在新实例上重新获得一整个阈值（默认一天 200 次）。重叠期阈值按实例数放大 | 排空期等同于今天重启时的清零。管理员解除封禁只作用于应答的那个进程：并存期间一次解除可能没解到实际拒绝请求的实例 |
| 身份未解析时的粗粒度熔断 | 进程内 | 同上 | 同上 |

**这一节现在的结论只有分类，没有"可接受"。** 进入实现之前需要对每一类给出下面之一，并经评审：

- 证明偏差在某个明确的上界之内并且可以接受（给出数字和依据）；
- 或者改为跨进程可见。已有一个可参考的做法：每个进程定期把在途数发布到数据库（F18），
  费用预留和并发计数可以用同样的方式让其他实例看到；
- 或者限制发布形态来避免它（例如只允许排空期、不允许重叠期；或排空期内对在旧实例上有在途请求的用户收紧新实例的放行）。

费用预算是其中最需要先解决的一类，因为它的偏差是钱，并且在数据库不健康时没有上界。

### 6.6 新旧并存的其他约束

| # | 约束 | 依据 |
|---|---|---|
| C1 | **数据库结构**：迁移在新实例启动前执行，旧代码必须能在新结构上工作。先扩展、后收缩的规则已经覆盖 | 迁移设计 §5.1、§7 |
| C2 | **配置和文档**：新旧实例读同一份数据库配置。并存期间管理员保存的内容，旧实例必须读得懂或安全地忽略。一个发布如果改变了已存配置的格式，要像结构变更一样分两个版本做 | 待核实：旧版本对未知字段的处理需要逐类检查 |
| C3 | **后台任务**：排空中的实例不再领取新工作。批处理按租约设计，可以由新实例接手。没有按多进程设计的任务（告警评估、邮件调度、价格同步）并存期间不能重复触发 | 待核实：实现前列出全部后台任务并逐个标注 |
| C4 | **请求级的版本交替**：重叠期同一个客户端的连续请求可能先后落在旧版本和新版本上，相邻两个发布在 API 行为上必须能这样交替 | 任何滚动发布的通用要求 |
| C5 | **回滚**：回滚时旧镜像重新启动、新镜像排空，约束与正向相同。兼容下限的检查决定旧镜像能否启动 | 迁移设计 §7 |

## 7. 已有前端交接机制与后端方案的关系

前端的新旧 Pod 交接在发行版里实现，不在本仓库，我没有读到它的实现。下面的描述来自评审中给出的说明。

两者是不同的机制，不能等同：

| | 已有的前端交接 | 本文的后端方案（§6） |
|---|---|---|
| 确认发生在什么时候 | **删除旧实例之前**，确认已摘流、请求已完成，然后才删除 | 第 1 版写的是进程**收到停止信号之后**自己排空，与前端交接不是一回事。第 2 版改为停止之前由编排确认（§6.2），在这一点上与前端交接同一个思路，但实现是否相同没有核实 |
| 谁判断"完成" | 发行版的发布流程 | 发行版的发布流程，依据网关报告的排空状态（§6.3） |
| "完成"包含什么 | 入口不再分配、已有请求结束 | 多出一项：计费和日志收尾（X3）。另有批处理条目、后台任务 |
| 超时怎么办 | 没有核实 | 三种处理和四种结果（§6.4） |
| 并存期间的共享状态 | 前端无状态 | 有，且未解决（§6.5） |

可以复用的是原则和验证方法：

- "入口停止分配"和"已有请求完成"是两个独立条件，分别确认。X1、X2 沿用这个划分。
- 先确认、后删除。
- 测试环境里"长流跨实例替换"的验证场景，改成 §8 的验收：加上"新请求同时成功"和"不许重试"。
- 入口在实例被摘除时的行为（何时停止分配、是否保留已有连接）是入口的属性，前端交接时得到的结论可以作为
  E9 的起点，但要在后端的 Service 上重新实测，不能直接沿用。

不能直接沿用的：前端交接的实现、它的时限取值、它对"完成"的判断方式。后端的每一项都要按 §6 单独实现和验收。

另外两点与阶段一有关：

- Next 自己的停止行为是等进行中的请求结束（F24）。这是核心已有的，不变。
- 前端旧实例的宽限时间在分流稳定之前保持不变。回滚后流量会重新经过控制台，届时仍然需要它覆盖长流。

## 8. staging 验收与回滚

### 8.1 工具

核心提供一个探针脚本，输入是基础地址和一个 API key，从外部运行：

- 用原始 HTTP 客户端，不用 SDK，**不重试**。每一次失败都计数。
- 长流：记录每一帧的到达时间；用带序号的合成上游时逐帧核对内容；检查结束标记
  （Chat Completions 的 `[DONE]`、Messages 的 `message_stop`、Responses 的 `response.completed`）
  和 usage 是否齐全。
- 新请求：按固定速率持续发出短的流式和非流式请求，覆盖 `/v1/chat/completions`、`/v1/responses`、
  `/anthropic/v1/messages`。
- §5 的各项检查。
- 健康检查只作为辅助信号记录，不作为通过依据。

合成上游需要按固定间隔发出固定数量的帧。example 的假模型服务没有帧间隔（F26），实现时给它加上这个参数，
验收和 §9 的实验共用。

### 8.2 阶段一的场景

每个场景开始前先起一批长流，长度覆盖整个操作再加余量；同时保持新请求的固定速率。

| # | 操作 | 对 staging 的影响 | 说明 |
|---|---|---|---|
| S1 | 发布新的控制台镜像 | 与一次普通的前端发布相同 | 主场景 |
| S2 | 强制结束控制台进程 | 网页和浏览器接口短暂不可用 | 模拟崩溃 |
| S3 | 控制台完全停止 60 秒后恢复 | 网页和浏览器接口不可用 60 秒 | 最强的独立性证明，也是 §5.2 的检查点 |
| S4 | 撤掉分流规则，再加回来 | 取决于 H6：可能打断当时经入口的在途流 | 验证回滚本身 |
| S0 | 对照：在**原路径**上重复 S2 | **会打断当时所有经控制台的推理请求**，包括其他人的 | 探针必须报告流被打断。一个测不出失败的测试不能证明通过 |

S0、S2、S3、S4 是故障注入，会影响 staging 上的其他使用者。它们不随日常发布执行，需要单独安排执行窗口：
事先通知、选定时间、指定执行人，并在窗口结束后确认 staging 恢复正常。S0 的影响最大，单独排一个窗口。
步骤 0 的 A/A 校准（§9.2）不注入故障，不需要窗口。

### 8.3 通过标准

- S1 到 S3：没有一个长流被打断或内容不完整；新请求的失败数为 0。
  如果操作窗口之外本来就有偶发失败，以操作前同样时长的基线为准，窗口内不得更高，并逐条说明原因。
- 每个长流在 `api_logs` 里有一行，usage 完整，费用已记入。
- 网关日志的 `peer_ip` 与入口的访问日志都显示这些请求由入口直接送达（§5.1 的路径证明）。
- S3 和 S1 期间 §5.2 的检查通过：网关就绪不变，身份解析不变，不需要重启网关。
- S4：如实记录撤规则时在途的流是否受影响。不受影响则回滚可以随时做；受影响则回滚步骤里写明影响范围。
- S0 确实测出了失败。
- §5 的检查全部通过，已知变化（错误体、两个响应头）与本文列出的一致，没有多出来的。

阶段二的验收用同一个探针，把操作换成后端发布，并按 §6.4 的四种结果判定：只有"无损成功"算通过。
长流完整结束，新请求由新实例成功处理，停止时在途数和未写入都为 0，并存期间没有重复的后台任务，
§6.5 里选定的方案各有对应的检查。

### 8.4 回滚

阶段一的回滚是撤掉入口上的两条规则，流量回到控制台的内置转发。不需要回退镜像。前提：

- 控制台镜像保留 `/v1`、`/anthropic` 的转发（本文不删除它）。
- 网关对控制台的信任配置保留。
- 前端的宽限时间没有缩短（§7）。

触发条件：分流路径的错误率高于基线；客户端身份的 `unknown` 比例上升；网关就绪因前端变化而抖动；
出现 §5 以外的行为差异。

## 9. latency 对照实验

### 9.1 要回答的问题

绕过控制台之后，端到端 latency 有没有可测量的变化，在哪些条件下有，这个变化对用户有没有意义。
H7 是假设，不是结论。实验结果不决定是否分流（目标一独立成立），除非分流路径出现回退（§9.6）。

### 9.2 两条路径同时可达

- **外层（用户实际看到的）**：同一个入口上配两个主机名，其余配置完全相同。一个把所有路径交给控制台（原路径），
  一个启用分流（新路径）。同一台客户端、同一时间段内交替向两边发请求（ABBA 顺序），用来抵消模型服务负载和
  网络随时间的变化。
- **内层（只看这一跳）**：从同一网络内部直接请求控制台的 `/v1` 和网关的 `/v1`，去掉入口和公网的噪声，
  单独量出控制台这一跳的开销。
- **校准（A/A）**：正式比较之前，两个主机名都指向原路径跑一遍。两边的差就是这套测量的噪声底。
- 每个请求按 §5.1 的路径证明抽查，确认确实走了预期的路径。

### 9.3 变量控制

| 变量 | 控制方式 |
|---|---|
| 模型与上游波动 | 主要结论用合成上游：固定首字延迟、固定帧数、固定帧间隔、固定帧大小。另用一个真实模型做一组确认，只看趋势 |
| 输出长度 | 合成上游固定。真实模型固定 `max_tokens`、`temperature=0`，事后核对两边的 `completion_tokens` 相同，不同的样本剔除并报告数量 |
| 缓存 | 真实模型分两组，各自单独报告：前缀每次相同（预热后全部命中）和前缀带随机串（全部不命中）。不混在一起 |
| 路由 | 两边用同一个 API key、解析到同一个客户端身份；记录每个请求实际落到的 endpoint，按 endpoint 分层比较 |
| 网关内部耗时 | 用网关日志的 `duration_ms` 做对照：客户端总耗时减去它，得到路径上的开销 |
| 请求体大小 | 小请求体（约 1 KB）和大请求体（约 1 MB）各一组，因为原路径上请求体要经过 Node |
| 客户端与网络 | 同一台机器、同一时间段、交替发送；连接复用策略两边相同并写明 |

### 9.4 指标

每个请求由客户端记录时间戳：

- TTFT：发出请求到第一个带内容的事件。保活注释不算。同时记录到第一个字节的时间。
- 流式接收间隔：每个流内相邻两帧的间隔。合成上游下再减去发出间隔，得到路径引入的抖动。
- 整请求耗时：流式和非流式分别统计。
- 错误：非 2xx、传输错误、被截断的流，分别计数，并按 §9.6 归因。失败的请求不进入 latency 统计。

每一项报告 P50、P95、P99，以及两条路径之差的置信区间。每个场景每条路径至少 1000 个请求；
少于 2000 个时不报告 P99。

### 9.5 场景

| 场景 | 负载 |
|---|---|
| 低并发 | 同时 1 个请求 |
| 正常负载 | 并发数取该部署实测的常态值和高峰值（来自 `api_logs`） |
| 网页服务有负载 | 在正常负载之上，另一个发生器以固定速率请求控制台的页面和浏览器接口，速率取实测页面高峰的若干倍。此时新路径不应受影响，这正是要验证的 |
| 压力（可选） | 并发提高到常态的 10 倍，找出原路径开始变差的点 |

"网页服务有负载"和"压力"两个场景会让 staging 的网页变慢，与 §8.2 的故障注入一样需要安排窗口。

### 9.6 判读：候选阈值

下面是**候选值**，附理由。它们经评审确认后冻结，冻结之后才跑 A/B；看到 A/B 数据之后不再修改。
A/A 的噪声底是测量出来的量，它的计算方法在这里先定下，数值在校准后填入。

判读分两层，分别回答两个不同的问题。

**第一层：统计上有没有差别。** 两个条件同时满足才算"有差别"：

- 两条路径之差的 95% 置信区间（按交替配对做自助法）不包含 0；
- 差的绝对值大于噪声底。噪声底定义为 A/A 校准中同一指标两边之差的 95% 置信区间两端绝对值里较大的一个。

不满足时，结论是"没有可测量的差别"，这是合法结论。

**第二层：这个差别对业务有没有意义。** 统计上有差别之后才看这一层：

| 指标 | 候选阈值（绝对值与相对值取较大者） | 理由 |
|---|---|---|
| TTFT，P50 | 20 毫秒，或基线的 5% | 20 毫秒大约是一次网络往返，低于人对流式文字开始出现的感知。相对值是为了在基线很高的模型上不把微小变化当成改善 |
| TTFT，P95 和 P99 | 50 毫秒，或基线的 10% | 尾部估计的波动更大，阈值放宽；同时尾部是用户会抱怨的部分，所以单独判 |
| 路径引入的帧间抖动，P99 | 50 毫秒 | 帧间隔通常在几十毫秒，多出 50 毫秒开始能看出文字一顿一顿。入口如果缓冲了响应，只会在这个指标上表现出来 |
| 整请求耗时（去掉网关内部耗时后的路径开销），P50 | 20 毫秒 | 路径开销是固定的附加量，与生成时长无关，所以只用绝对值。相对整个请求它通常不到 1%，即使统计上成立也可能没有业务意义，这一点在结论里照实写 |
| 同上，P95 | 50 毫秒 | 同 TTFT 尾部 |
| 大请求体的上传耗时，P50 | 50 毫秒 | 原路径上请求体要经过 Node 再转发，这是最可能出现差别的地方 |

每个指标的结论是下面四种之一：没有可测量的差别；可测量但低于业务阈值；有业务意义的改善；回退。

**回退的处理。** 分流路径在任一场景、任一指标上比原路径差且超过业务阈值，就是回退：先查清原因，
解决并重测之前不推进到生产。分流路径少一跳，没有理由更慢，出现回退通常意味着入口配置有问题
（例如缓冲）。差别低于业务阈值的变差只记录，不阻塞。

**错误率单独设门槛，不与 latency 合并判读。**

| 门槛 | 候选值 | 理由 |
|---|---|---|
| 路径造成的错误 | 分流路径上为 0。整个实验每条路径累计不少于 3000 个请求 | 路径造成的错误指：入口自己返回的 5xx、连接被重置、流被截断，且网关日志显示该请求成功或根本没有收到。3000 个请求里出现 0 次，能把真实错误率的 95% 上界压到约 0.1%。出现任何一次都逐条查明原因，修复后整组重跑 |
| 总错误率 | 分流路径不高于原路径，差值不超过 A/A 校准中两边的差 | 上游和网关自己的错误两边应当相同；不同就说明路径有影响 |
| 样本有效性 | 任一场景里失败请求超过 1% 时，该场景的 latency 结果作废重跑 | 失败的请求被排除在 latency 统计之外，排除太多会让分位数失真 |

## 11. 风险与待确认事项

风险：

- **入口规则写宽了，暴露网关的未公开路径**（F5）。由探针从外部检查（§5.1），并要求 E7。
- **清单和入口规则漂移**。新增公开路径时，分流前缀之内的不需要动入口；之外的走控制台。
  只有新增或移动分流前缀时才需要同时改入口，这时必须重跑探针。
- **两种拓扑都要测**。核心的自动测试只覆盖内置转发；入口分流靠发行版在 staging 上跑探针。
  网关侧的行为（§5 里由网关保证的各行）在核心测试里覆盖。
- **网关不可达时的错误体变了**。SDK 按状态码处理，但自己解析错误体的调用方会看到不同的内容。
- **代理发现模式下，分流可能反而把前端的停止变成推理的中断**（§5.2 的原因 2、3）。在 T1 到 T5 满足之前，
  这种部署不启用分流。

待确认：

1. 第一个启用分流的发行版用的是什么入口，能否满足 E1 到 E9。**由部署侧补实测证据，保持待确认。**
2. 该发行版实际的代理发现配置：是否启用、固定的是哪个控制器的 UID、入口是不是 Pod、今天跑几个网关实例。
   **由部署侧补实测证据，保持待确认。** 它决定步骤 1b 是否进入最小范围，以及 T5 用哪种形式。
3. §5.2 的 T3（前端来源失效时网关保持就绪、只让来自前端的请求身份变成 `unknown`）是否同意。
4. §9.6 的候选阈值，评审后冻结。
5. §6.5 每一类的处理方案。这是阶段二的门槛，不在本期。
